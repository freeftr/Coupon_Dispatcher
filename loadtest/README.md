# 스파이크 부하 테스트: 발급 API 응답 지연

이벤트 오픈 순간처럼 짧은 시간에 수천 명이 한 번씩 발급 요청을 보낼 때, API 가 얼마나 늦게 응답하는지 잰다. 대상은 세 가지다.

| 이름 | 커밋 | 경로 | 요청 안에서 하는 일 |
|---|---|---|---|
| A-직접 발급 | `ed4d7ef` (main) | `POST /api/v1/coupons/{couponId}?memberId=` | 회원·쿠폰 조회 → Redis Lua 로 수량·중복 검증 → MySQL INSERT → 이력 이벤트 |
| A-대기열 접수 | `ed4d7ef` (main) | `POST /api/v1/coupons/{couponId}/queue?memberId=` | 회원 조회 → Lua 로 ZSET 등록 → 순번 즉시 응답. 발급은 스케줄러가 1초마다 10명씩 |
| B-옛 커밋(DB만) | `ae00c90` | `POST /api/v1/coupons/{couponId}?memberId=` | 회원·쿠폰 조회 → 중복 EXISTS → 발급 수 COUNT → INSERT. 트랜잭션·락 없음 |

B 는 Redis 를 들이기 직전 커밋이다. `d1eb29c`(Redis 로 발급 로직 교체)의 부모 `685d80a` 는 Redis 의존성만 더한 커밋이라, 그보다 한 칸 앞인 `ae00c90`(#13 머지)을 골랐다. 단일 모듈이고 Redis·Kafka 를 쓰지 않으며, 고치지 않고 그대로 빌드됐다.

## 결론

- 초당 500명까지는 셋 다 p95 10ms 안쪽이다. 차이가 드러나는 건 초당 2,000명부터다.
- 초당 2,000명에서 직접 발급의 p95 는 348~794ms 로 뛰었다. 이때 Tomcat 스레드 200개 중 190개가 Hikari 커넥션(10개)을 기다리고 있었다. 병목은 Redis 가 아니라 DB 커넥션 풀이다.
- 같은 부하에서 대기열 접수는 3회 중 2회가 p95 16~119ms 였다. 1회는 p95 839ms 로 직접 발급과 비슷하게 밀렸는데, 대기열 진입도 `validateMemberExists` 로 MySQL 을 한 번 읽어 같은 풀을 기다렸기 때문이다(그 회차 대기 스레드 191).
- Redis 도입 전 코드는 초당 2,000명에서 p50 2.4~5.6초, 처리량 721~1,417 req/s 로 부하를 따라가지 못했다. k6 가 VU 6,000개를 다 써서 시작조차 못 한 사용자가 회차마다 986~8,693명 나왔다. 수량 1,000장인데 실제 발급 행은 1,002~1,004개로, 동시 요청이 COUNT 검사를 함께 통과해 초과 발급됐다.
- 대기열의 실제 발급 완료는 설계대로 초당 10명이라 1,000장에 104~110초가 걸렸다. 사용자는 바로 순번을 받지만 결과까지는 이만큼 기다린다.

## 시나리오

- 쿠폰 1장(id 1, 수량 1,000)을 두고, 매초 새 사용자 `RATE` 명이 10초 동안 들어와 각자 한 번 요청한다(k6 `constant-arrival-rate`). memberId 는 반복 순번으로 정해 모두 다르다.
- 부하 두 단계: 초당 500명 × 10초(5,000명), 초당 2,000명 × 10초(20,000명). 세 대상에 같은 부하를 준다.
- 회차마다 `reset.sh` 로 Redis FLUSHALL, 쿠폰·발급 기록 TRUNCATE, 쿠폰 재생성(대기열은 활성화까지)을 한 뒤, 같은 경로로 1,000건(초당 200)을 흘려 JIT·풀을 데우고, 다시 초기화하고 잰다.
- 각 단계를 3회 돌렸다. 순서는 회차마다 직접 → 대기열 → 옛 커밋.
- 응답 분류
  - 성공·접수: 200·204
  - 업무 거절: 품절(1003)·중복(1002·4001) 코드를 담은 4xx. 현재 코드는 400, 옛 커밋은 404 로 돌려준다. 실패로 세지 않는다
  - 실패: 5xx, 타임아웃(30초)·연결 오류. 실패율은 이것만 센다
- 곁들인 지표
  - Hikari 대기 스레드: 스파이크 첫 4초 동안 0.5초마다 `jcmd Thread.print` 를 떠 `HikariPool.getConnection` 에 걸린 스레드 수의 최댓값
  - MySQL: 0.5초마다 `SHOW GLOBAL STATUS` 의 `Threads_running` 최댓값. `Threads_connected` 는 회차 내내 21~30 이었다(두 앱 풀 10+10 과 모니터 세션)
  - 실제 발급 행: 측정 뒤 `coupon_member` 행 수. 1,000 을 넘으면 초과 발급이다

## 해석

1. 직접 발급의 지연은 Redis Lua 가 아니라 요청마다 DB 커넥션을 잡는 데서 나온다. 2,000/s 에서 커넥션 10개를 두고 Tomcat 스레드 190개가 줄을 섰고, 실제 발급된 요청의 p95 는 509~676ms 였다.
2. 대기열은 DB INSERT 를 요청 밖으로 빼서 접수 p50 을 1~2ms 로 지켰다(3회차 제외). 다만 진입 시 회원 존재 확인이 MySQL 을 읽고 OSIV 가 요청 내내 커넥션을 쥐고 있어, 풀이 막히면 접수도 함께 느려진다(3회차). 회원 확인을 Redis 로 옮기거나 OSIV 를 끄면 이 회차 같은 꼬리를 줄일 수 있을 것으로 보이지만, 이번에는 재지 않았다.
3. Redis 도입 전 코드는 같은 부하에서 p95 가 3.2~7.4초로, 직접 발급(0.35~0.79초)보다 중앙값 기준 약 7배 느렸고 초과 발급(2~4장)도 났다. Redis 로 수량 검사를 원자화한 효과가 지연과 정합성 양쪽에서 보인다.
4. 2,000/s 에서는 회차 편차가 크다(직접 발급 p50 1.5~114ms, 대기열 p95 16~839ms). 풀이 막히는 순간이 회차마다 조금씩 달라서다. 한 회차 숫자만 인용하지 말고 범위로 본다.

## 못 잰 것

- Hikari 의 pending 수를 메트릭(Actuator·JMX)으로 연속 수집하지 않았다. 스레드 덤프 표본으로 대신했다. 덤프 한 스레드에 `getConnection` 프레임이 두 줄 찍혀, 첫 측정은 줄 수(380)로 기록됐다. 이후 따로 덤프를 떠 스레드 190개임을 확인하고 결과 JSON 을 2로 나눠 고쳤다. `run.sh` 는 지금 스레드 블록 단위로 센다.
- 대기열 사용자 개인별 「접수 → 결과 확인」 시간은 재지 않았다. 발급 완료까지의 전체 시간(첫 발급 ~ 1,000번째 발급)만 기록했다.
- 배치 모듈(이력 컨슈머)은 띄우지 않았다. A 앱은 Kafka 로 이벤트를 보내기만 한다.
- 다른 머신이나 앱·DB 를 분리한 환경에서는 재지 않았다.

## 실행 방법

리포 루트에서 실행한다. JDK 17 이 필요하다(Gradle 이 받아둔 `~/.gradle/jdks/...` 의 JDK 를 써도 된다).

```bash
# 0. 도구
brew install k6

# 1. 인프라
docker compose -f loadtest/docker-compose.yml up -d

# 2. A 앱(main) 빌드·기동: 18080
./gradlew :api:bootJar -x test
java -Xms1g -Xmx2g -jar api/build/libs/api-0.0.1-SNAPSHOT.jar \
  --spring.config.additional-location=file:loadtest/application-loadtest.yml &

# 3. B 앱(ae00c90) 빌드·기동: 18081, DB 는 coupon_legacy
git worktree add ../cd-legacy ae00c90
(cd ../cd-legacy && sh ./gradlew bootJar -x test)
java -Xms1g -Xmx2g -jar ../cd-legacy/build/libs/coupon-0.0.1-SNAPSHOT.jar \
  --spring.config.additional-location=file:loadtest/application-loadtest.yml \
  --server.port=18081 \
  '--spring.datasource.url=jdbc:mysql://localhost:13306/coupon_legacy?createDatabaseIfNotExist=true&useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=Asia/Seoul' &

# 4. 회원 시드(관리자 id 1 + 회원 20,500명). 앱이 테이블을 만든 뒤 실행
./loadtest/seed.sh http://localhost:18080 coupon 20500
./loadtest/seed.sh http://localhost:18081 coupon_legacy 20500

# 5. 측정: run.sh <direct|queue|legacy> <초당 사용자 수> <회차>
export JCMD=/path/to/jdk-17/bin/jcmd   # Hikari 대기 표본용. 없으면 APP_PID 를 빼고 돌린다(값 -1)
for rate in 500 2000; do for round in 1 2 3; do
  APP_PID=$(pgrep -f api-0.0.1-SNAPSHOT.jar) ./loadtest/run.sh direct $rate $round
  APP_PID=$(pgrep -f api-0.0.1-SNAPSHOT.jar) ./loadtest/run.sh queue  $rate $round
  APP_PID=$(pgrep -f coupon-0.0.1-SNAPSHOT.jar) ./loadtest/run.sh legacy $rate $round
done; done

# 6. 표 만들기
python3 loadtest/summarize.py

# 7. 정리
pkill -f api-0.0.1-SNAPSHOT.jar; pkill -f coupon-0.0.1-SNAPSHOT.jar
docker compose -f loadtest/docker-compose.yml down
git worktree remove ../cd-legacy
```
